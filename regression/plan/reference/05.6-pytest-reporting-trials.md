# 5.6 Pytest wiring

> Part of the [regression plan](../README.md). Section numbers (§5.9, §6.U, D12, …) are global across the plan; the README's section map says which file holds each one.


- Markers: `t1`, `t2`, `t3`, `t4`, `t5`, `live`, `needs_postgres`, `needs_firestore`, `darwin_only`, `slow`, `quarantine`, `case(id)`.
- Options, registered once in `regression/plugin.py` (loaded by `-p regression.plugin` in `pytest.ini`): `--live` (collect T4/T5), `--record` (T3 recorders), `--update-golden` (rewrite goldens; refuses in CI), `--trials N`, `--suite NAME`, `--agent-url URL`. The ledger plugin adds `--ledger-dir PATH` and `--no-ledger` to every pytest run.
- YAML scenarios are collected by a pytest plugin (`pytest_collect_file`), so each scenario is a test item with its id, `-k` works, and xdist parallelizes them.
- Commands:

```bash
uv run pytest tests -n auto                                       # tier 1 only (fast inner loop)
uv run pytest tests regression -m "t1 or t2 or t3" -n auto      # all deterministic tiers, every push
uv run pytest regression/t2 -k gateway                            # one driver
uv run pytest regression --live --suite smoke --agent-url http://127.0.0.1:8787
uv run python -m regression.t5 --suite coding_hard --trials 8 --agent-url http://127.0.0.1:8787
uv run pytest regression/t3 --record -k ollama_cloud              # re-record the Ollama wire cassette (OLLAMA_API_KEY)
```


## 5.7 Reporting

- T1–T3: plain pytest output; JUnit XML for CI.
- T4: scorecard markdown (successor of `evals/report.py`), run JSON in `t4/runs/` (gitignored), CI artifact. Run JSON keeps full tool args (today `args_summary` is truncated to 300 chars), so any T4 run can be converted into a T3a cassette.
- T5: per-scenario table with k/N, Wilson 95% interval, baseline k/N, verdict.
- All tiers: every failure also goes to the failure ledger in `test-runs/` (5.9), so there is one place to look regardless of which tier or report format produced it.


## 5.8 T5 statistics

- A trial run repeats one T4 suite N times: `uv run python -m regression.t5 --suite <t4 suite> --trials N`.
- Baselines are keyed `(T4 suite[@verifier config], provider, model)`: `regression/t5/baselines/coding_hard__ollama-cloud__glm-5.3-flash.json`, `regression/t5/baselines/drift@verifier-judge__ollama-cloud__glm-5.3-flash.json`. A run against a different key never compares to it.
- Per scenario, two classes, assigned by the class lists `regression/t5/suites/{reliability,capability,drift}.yaml` (which also carry the T5 case IDs). A scenario in no list counts as capability.
  - **Reliability**: pass^N. All N trials must pass. Use for harness-visible behaviors a model should always manage (e.g. calls `read_file` when asked to read).
  - **Capability**: report pass k/N with a Wilson 95% interval. **Fail** when the baseline rate is above the upper bound of the current interval. **Warn** when the point estimate drops by ≥ 0.2.
- Default N = 8; 5 for a suite whose scenarios are all reliability. Pace with `EVAL_SCENARIO_DELAY_SEC` as today.
- Baselines are updated only by an explicit `--update-baseline` run, committed in its own PR with the scorecard attached.
