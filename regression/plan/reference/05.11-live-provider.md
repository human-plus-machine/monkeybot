# 5.11 Live provider and credentials (T4, T5, and recording)

> Part of the [regression plan](../README.md). Section numbers (§5.9, §6.U, D12, …) are global across the plan; the README's section map says which file holds each one.


**Owner decision (2026-10-25):** every live run uses Ollama Cloud with the `OLLAMA_API_KEY` that is already in the owner's local environment. This settles D1.

| Use | Provider / model | How it is configured |
|---|---|---|
| T4 agent (every suite) | `ollama-cloud` / `glm-5.3-flash` | `regression/t4/agent/monkeybot_config/monkeybot*.yaml` (already the smoke agent's model) |
| LLM judge (T4 `metrics`, `min_score`) | `ollama-cloud` / a **different, larger** Ollama Cloud model (D12) | `regression/t4/eval_config.yaml`: `judge_provider: ollama-cloud`, `judge_model: <D12>`. The existing scorer already supports this (`GPTModel` against `https://ollama.com/v1` with `OLLAMA_API_KEY`). `JUDGE_PROVIDER` / `JUDGE_MODEL` env still override. |
| Verifier judge config (`monkeybot.verifier-judge.yaml`) | same Ollama key, verifier judge model set in that YAML | Section 6.K / T4-VER |
| T5 trials and baselines | same as T4 | Baselines keyed `<suite>__ollama-cloud__glm-5.3-flash.json` |
| T3a trajectory cassettes | recorded from T4 runs | So they are Ollama trajectories too |
| T3b wire cassette `ollama_cloud/glm_tool_turn.json` (T3-PROV-07) | `ollama-cloud` | `--record` with the same key. Because the Ollama provider streams through `providers/_openai_compat`, this cassette also exercises the parser shared by the NVIDIA, Fireworks and HuggingFace adapters. |

**Where the key comes from.** The gateway reads `OLLAMA_API_KEY` from the process environment; `core/layout.py` also loads `<agent root>/.env` without overriding existing variables. So live runs work when either:

1. the key is exported in the shell that starts the run (the owner's setup), or
2. it is in `regression/t4/agent/.env` (gitignored; never committed).

The T4/T5 runners do **not** read or copy the key anywhere else, never print it, and the ledger scrubber (5.9) redacts it from any record.

**Preflight, instead of a silent skip.** Today the workflow prints a warning and skips when its key is missing, which looks like a pass. The new runners check before starting the agent:

- If `OLLAMA_API_KEY` is missing: exit non-zero with `OLLAMA_API_KEY is not set (export it or put it in regression/t4/agent/.env)`, and write one ledger record with `kind: run_error`, so the run file shows the run never started.
- If the key is set but Ollama Cloud rejects it, or the model is unavailable, a single cheap `stream` call fails first with the provider's error text. This is the same check as `T4-PROV-01`, which now runs at the start of every live suite.

**Rate and cost.** T5 runs suites N times (default N = 5 or 8), all on one key. Pacing stays on `EVAL_SCENARIO_DELAY_SEC`, and the scorecard reports token totals per run. Ollama Cloud's exact limits for this key are not verified (section 2.3). If trials hit them, lower `--trials` or split suites across nights; do not swap in another provider, because the baselines are keyed to this one.

**What this rules out, and how each case is handled:**

| Case | Needs | Handling |
|---|---|---|
| `T4-PROV-01 provider_live_matrix` | keys for every provider | Default is Ollama Cloud only (it becomes the live preflight). Other providers run only if their key happens to be set; a missing key is a skip with its reason, not a failure. |
| `T4-RT-01 gemini_live_smoke` | GCP credentials (Ollama has no realtime voice API) | Moved to `docs/testing.md` §9 "Deferred coverage". Realtime stays covered by `T1-RT-01` and `T2-RT-01..07` against the realtime mock. |
| T3b wire cassettes for OpenAI, NVIDIA, Anthropic, Gemini, Bedrock (`T3-PROV-01..05`, and those families in `T3-PROV-06`) | each provider's key to record | Not recorded with the Ollama key. See D13. Until they exist, the adapters keep their T1 coverage (`T1-PROV-01..10`, `tests/unit/providers/**`). |
